诊断结论：B-Scan 的噪点是「最近邻抽稀」造成的显示伪影，不是数据本身的问题

我读了 `sliceView.js` 的渲染路径，并用真实瓦片数据做了仿真验证。

### 噪点怎么来的

B-Scan 显示的是固定通道的 (X, Z) 切片没错，数据也是原始 int16→float32 体素，**但显示时经过了两次「最近邻抽稀」，每个屏幕像素最终只取了约 68 道里随机 1 道的值**：

1. **网格抽稀**：源 X=45307 道 → `gridX=2048`（`sliceView.js:33`），`_rebuild` 里对每道算 `gxBase = round(...)`，落在同一列的 ~22 道**后写的覆盖先写的**，等于任意挑 1 道；
2. **canvas 二次抽稀**：2048 列 → 660px 画布（`_renderCanvas` 里 `gx = round(px/cw*gw)`），每像素又任意挑 1 列。

450 MHz 天线 `AUTOSTACKS: 1`（`明星路_001_A01.iprh`），单道噪声本来就是高频的，逐级任意采样 → 椒盐噪点铺满整个雷达图。

### 实测证据（真数据，通道 0，X[0,8192) 全深度）

相邻列均绝对差（越小越平滑）：

| 分辨率/方式 | 粗糙度 |
|---|---|
| 全分辨率 X=8192 | **11.9** |
| 最近邻抽到 2048（现状） | 25.0 |
| 箱平均抽到 2048（建议） | 19.3 |
| 再抽到 canvas 660px·最近邻链路（现状） | **33.6** |
| 再抽到 canvas 660px·箱平均链路（建议） | **22.1** |

同一分辨率下，最近邻比箱平均粗糙 **34%**——全分辨率时相邻道高度相关（11.9），说明**数据本身不脏**，噪点是抽稀方式引入的。

### 为什么主视图看起来干净，而 C-Scan 更脏

- **主视图**：GPU 三线性插值（`brickRenderer.js:107`）+ 射线积分按不透明度累加，噪声被沿视线平均掉了。
- **C-Scan**：固定深度横跨 14 个通道，通道间本来就独立（天线不同），加上同样的抽稀，所以更脏——你理解的没错。
- **B-Scan**：只有 1 个通道、没有积分平均，抽稀伪影就完全暴露了。

### 修复建议

把 `sliceView.js:_rebuild()` 里 B/C-Scan 的 stamp 逻辑从「最近邻 last-write-wins」改成**箱平均**（每格累计和+计数，最后取均值），同时保留「细级覆盖粗级」的语义（每格记录来源 LOD，仅当更细级才重置累加）。这是显示层改动，**不需要重新生成 dataset**，也不会改变 3D 主视图。
